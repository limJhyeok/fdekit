# Build from Requirements: 명세 → 점검 → 구현 → 제출

합의된 요구사항을 시간 안에 돌아가는 결과물로 만든다.
원칙은 하나다. **되돌리기 비싼 빈틈은 구현 전에 확정하고, 싼 빈틈은 AI에게 맡기고 테스트로 확인한다.**

## 시작 전
- 입력: `requirements.md`(필수), `conversation-log.md`, `problem-notes.md`, 문제 설명
- 시간: **남은 시간을 사용자에게 묻고**(타이머는 사용자가 본다), 아래 비율로 나눠 보여 준다. 에이전트는 경과 시간을 추측하지 않는다.

| 단계 | 남은 시간 대비 | 180분 과제에서 30분을 쓴 경우 |
|---|---|---|
| 1. 명세와 점검 | 약 10% | 15분 |
| 2. 설계 결정 + 3. 뼈대 | 약 10% | 15분 |
| 4. 요구사항 단위 구현 | 약 60% | 90분 |
| 5. 전체 점검·현업 공유 | 약 13% | 20분 |
| 6. 문서·제출 | 약 7%, 종료 10분 전에는 제출 시작 | 10분 |

- **밀리면 줄이는 순서:** 권장 요구사항 → 필수의 다듬기 → 필수 자체. 필수를 빼야 하면 담당자에게 알리고 다시 합의한다(`requirements-alignment` 7단계).

## 1. 명세와 점검

### 1-1. ACCEPTANCE.md 작성
`references/acceptance-template.md` 형식으로 쓴다.
- **먼저 ID를 정리한다.** 범위 제안에서 동의받은 기본 가정(노트의 Q-번호로만 남아 있는 것)은 시나리오를 쓰기 전에 `requirements.md`의 요구사항(R)·제약(C) ID로 올린다. 시나리오는 R·C ID에만 붙인다.
- 필수 요구사항과 **과제 고유 제약**마다 **정상 흐름 S1을 반드시** 쓴다. 예외 시나리오는 되돌리기 비싼 것만 쓰고, 나머지는 한 줄 목록으로 둔다.
- 제약은 종류에 따라 둔다.
  - 과제 고유 제약(담당자·자료에서 나온 것, 예: "사용자 데이터 원본 보관 금지"): ACCEPTANCE에 시나리오로
  - 환경 제약(실행 환경, 키 관리): ACCEPTANCE에 넣지 않고 `references/submit-checklist.md`로 확인
  - 확인할 수 없는 제약(작업 시간 등): 넣지 않음
- S1의 기대 결과에는 **관찰할 수 있는 결과만** 쓴다. 버튼 배치, 데이터 길이 상한 같은 구현 선택은 `DECISIONS.md`로 보낸다.
- **기대 결과 한 줄마다 근거 표시를 붙인다.** 이것이 이후 점검을 빠르게 만드는 핵심이다.
  - `[담당자 #n-m]` 대화에서 들은 것
  - `[문서]` 문제 설명·자료에 있는 것. 문제 설명이 제공한 환경(제공 API, 실행 환경)도 포함
  - `[합의 #n-m]` 응시자가 제안하고 담당자가 동의한 것 (범위 제안, 이해 확인 등)
  - `[결정]` 응시자가 정한 것 (근거나 이유를 괄호로). 합의 내용에서 응시자가 끌어낸 결론도 `[결정]`
  - `[미확정]` 근거도 결정도 없는 것
- 쓰다가 "이건 어떻게 되지?" 싶은 곳을 그럴듯한 문장으로 메우지 않는다. `[미확정]`으로 남긴다. 예: "고객의 말이 보인다"라고 쓰기 전에, 보이는지 들리는지 근거가 있는지 확인한다.
- `requirements.md`의 확인 방법 칸 끝에 시나리오 ID를 붙인다(`→ ACCEPTANCE.md R1-S1~S3`).

### 1-2. 새 컨텍스트에서 가정 점검
작성한 에이전트가 스스로 점검하지 않는다. 같은 맥락이 같은 가정을 다시 통과시킨다.
- Codex에서 독립 컨텍스트의 서브에이전트를 사용할 수 있으면 해당 기능으로 점검한다. 사용할 수 없으면 새 세션에서 실행할 점검 프롬프트와 입력 파일 경로를 준비해 사용자에게 전달한다. 같은 컨텍스트의 자기 점검을 독립 점검으로 기록하지 않는다.
- 프롬프트는 `references/spec-review-prompt.md`를 그대로 쓴다. 파일 경로만 넘기고, 작성 의도나 내 결론은 전하지 않는다.
- 결과: 근거 없는 가정을 **흐름·구조 / 기준·내용 / 예외** 셋으로 나누고, 흐름·구조는 **최대 5개**만 자세히 받는다.
- 점검 결과 반영 규칙:
  - **근거 표시 수정**(예: `[담당자]` → `[결정]`, 근거 번호 정정)은 바로 반영하고, 바꾼 줄을 목록으로 사용자에게 보고한다. 표시를 낮출 때는 `[합의]`에 해당하지 않는지 대화 기록에서 먼저 확인한다.
  - **내용·범위 수정**(기대 결과를 바꾸거나 빼기, 시나리오 추가·삭제)은 바로 반영하지 않는다. 1-3에서 사용자 판단을 받는다.

| 분류 | 예 | 처리 |
|---|---|---|
| 흐름·구조 | 입력·출력의 형태(소리/글), 한 번인지 주고받는지, 저장 여부, 화면 흐름, 외부 연동 | 구현 전에 확정 |
| 기준·내용 | 판정 기준, 피드백 항목, 문구 | 기본 가정으로 시작, 결과를 보며 조정 |
| 예외 | 권한 거부, 빈 입력, 네트워크 오류 | AI에게 맡기고 테스트로 확인 |

### 1-3. 사람이 읽을 곳만 제시
사용자에게 아래 세 가지만 보여 주고 판단을 기다린다. 전체 문서를 읽으라고 하지 않는다.
1. 점검 결과로 **바로 고친 근거 표시** 목록
2. 점검에서 나온 **흐름·구조 항목(최대 5개)**: 항목마다 "담당자에게 물을 것 / 직접 정할 것" 제안과 이유를 붙인다.
3. **필수 요구사항별 S1 목록**: 사용자는 S1마다 세 가지만 확인한다.
   - 입력은 어디서 어떤 형태로 오는가
   - 결과는 어떤 형태로 보이는가
   - 그 근거가 담당자인가, 합의인가, 내 결정인가

S1은 처음부터 끝까지 정독하지 않는다. **근거 표시에 따라 읽는 강도를 나눈다.**

| 표시 | 읽는 법 |
|---|---|
| `[미확정]` | 반드시 읽고 결정한다. 요구사항 머리말의 "미확정:" 줄에 요약되어 있다 |
| `[결정]` | 이유가 근거를 넓혀 쓰지 않았는지, 되돌리기 비싼지만 본다 |
| `[담당자]`, `[합의]`, `[문서]` | 건너뛴다 |

S1 정독은 리허설과 인수인계 문서에 필요한 이해를 만드는 가장 싼 방법이다. 이 단계를 생략하자고 제안하지 않는다.

### 1-4. 확정하고, 기다리지 않는다
- 담당자가 답할 수 있는 항목(기본은 업무 언어로 답할 수 있는 것, 담당자가 개발자이면 기술 제약도 포함): **한 메시지에 1~3개**로 묻는다. 작성 규칙은 `../problem-discovery/references/message-template.md`.
- 기술적 결정이거나 담당자가 답할 수 없는 항목: 직접 정하고 `DECISIONS.md`에 기록한다.
- 답을 기다리는 동안 **답과 상관없는 부분**부터 2·3단계를 진행한다. 답이 오면 `[미확정]`을 `[담당자 #n-m]`으로 바꾼다.
- 기한 안에 답이 없으면 기본 가정으로 진행하고 `[결정]`으로 바꾼 뒤, 5단계 공유 때 담당자에게 알린다.

## 2. 설계 결정 기록
`references/decisions-template.md` 형식으로 `DECISIONS.md`를 쓴다.
- 정할 것: 기술 스택(요청에 가장 적합한 스택 선정, 크게 요청 내용이 없을 경우 가장 익숙하고 빨리 띄울 수 있는 것), 화면 흐름(최소 화면 수), 데이터 흐름(저장하는 것/하지 않는 것), LLM을 쓰게 될 경우 쓰는 지점과 결과 형식, 미확정 사항 처리.
- **결정마다 요구사항·제약 ID와 이유를 단다.** 제약은 설계로 직접 옮긴다. 예: "데이터 원본 보관 금지 → 메모리에서만 처리, 디스크·DB에 쓰지 않음".
- **합의하지 않은 기능은 만들지 않는다.** 떠오른 아이디어는 `requirements.md`의 '제안'에 적고 넘어간다.

## 3. 처음부터 끝까지 이어지는 뼈대
- 입력 → 서버 → LLM(Optional) → 결과 표시가 가장 얇게라도 끝까지 이어지게 만든다.
- 실행 명령(`run.sh` 등)과 README의 실행 방법을 이때 확정한다. 새로 받은 상태에서 명령 하나로 뜨는지 확인한다.
- 키는 환경변수로만 읽고 `.env`는 `.gitignore`에 넣는다. 확인 후 커밋한다.

## 4. 요구사항 단위 구현
필수 요구사항을 우선순위대로 하나씩, 아래를 반복한다.
1. 구현 지시에 **요구사항 ID와 시나리오 ID**를 붙인다. 예: "R3을 구현해. ACCEPTANCE.md R3-S1, S2가 통과해야 해."
2. 자동화할 수 있는 시나리오는 테스트로 만든다. 테스트 이름에 시나리오 ID를 넣는다(`test_R3_S1_...`).
3. 테스트를 **직접 실행**하고, 서버를 띄워 화면에서도 한 번 확인한다. "됐다"는 보고만으로 넘어가지 않는다.
4. ACCEPTANCE.md의 '확인 결과 기록'을 갱신한다.
5. 통과하면 바로 커밋한다. 커밋 메시지에 요구사항 ID를 넣는다. 큰 변경을 몰아서 커밋하지 않는다.
6. **약점 카드를 `WEAKPOINTS.md`에 추가하고 사용자에게 보여 준다** (3~5분). 형식은 `references/weakpoints-template.md`.
   - 리허설 질문은 코드의 실제 동작, 특히 실패 경로에서 나온다. 의도한 동작을 답하면 오개념으로 감점된다. 제출 뒤 몰아서 코드를 읽으면 실패 경로가 너무 많아 다 볼 수 없다. 그래서 커밋마다 나눠서 쓴다.
   - 이번 변경의 **① 실패·timeout·잘못된 응답 ② 동시 요청 ③ 데이터가 남는 곳 ④ 테스트가 실제로 검사하는 범위**를 코드를 읽고 `파일:줄`과 함께 쓴다. 설계 문서나 지시문을 옮겨 적지 않는다.
   - 사용자는 카드의 `파일:줄`을 직접 열어 맞는지 확인한다. 사용자가 틀렸다고 하면 코드를 다시 읽고 고친다.
   - 사용자가 카드를 읽고도 설명하지 못하는 장치(재시도·큐·취소·동시성 제어 등)는 더 단순하게 만들 수 있는지 함께 제안한다. 설명할 수 없는 장치는 그 자체로 리허설 문제가 된다.

LLM을 쓰는 부분:
- 결과를 정해진 구조로 받는다(예: `{짚을 점, 근거 문장, 이유}`). 화면 표시와 테스트가 안정된다.
- S1과 경계 시나리오를 여러 번 돌려 결과가 흔들리는지 본다. 흔들리면 프롬프트에 기준과 경계 예시를 보강한다.
- 업무 기준(B-ID) 밖의 평가를 하지 않도록 프롬프트에 명시한다.

구현 중 새 빈틈이 나오면 1-2의 분류로 판단한다. 흐름·구조면 멈추고 확정한다. 나머지는 `[결정]`으로 기록하고 진행한다.

## 5. 전체 점검과 현업 공유
- 처음 쓰는 사람처럼 새 브라우저에서 안내 없이 시작부터 결과까지 가 본다. 예외 시나리오도 한 번씩.
- 제약을 다시 확인한다. 저장하면 안 되는 것이 어디에도 남지 않는지, 키가 코드와 git 기록에 없는지.
- 담당자에게 결과를 짧게 설명하고 반응을 받는다. `[결정]`으로 진행한 주요 가정도 이때 알린다. 범위가 바뀌는 요청이면 이후 과제로 남기고 그렇게 합의한다.
- 시간이 남으면 권장 요구사항을 넣는다.

## 6. 문서와 제출
`references/submit-checklist.md`를 따른다.
- README: 실행 방법, 요구사항 ID ↔ 기능 대응, 합의한 범위와 하지 않은 것(이유), 기본 가정·미확정 사항, DECISIONS.md 링크.
- **문서와 코드를 대조한다.** 문서에 있는데 구현되지 않은 것은 지우거나 "미구현"으로 고친다.
- `WEAKPOINTS.md`를 최종 코드와 대조하고, 사용자가 제출 직전에 5분 동안 다시 읽게 한다.
- 체크리스트를 통과한 뒤 제출한다.

## 사용자에게 보고 (단계마다)
- 시작 전에 나눈 단계별 예산(분). 밀리는지는 사용자가 타이머로 판단하고, 밀리면 위의 '줄이는 순서'를 따른다
- 끝난 것, 남은 필수 요구사항
- 사용자 판단이 필요한 것 (1-3의 목록, 범위 축소 여부 등)
