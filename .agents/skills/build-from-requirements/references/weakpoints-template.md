# WEAKPOINTS.md 형식

리허설 질문은 코드가 **실제로 하는 일**, 특히 실패 경로에서 나온다. 의도나 설계 문서를 옮겨 적은 카드는 쓸모가 없다. 오히려 오개념을 외우게 만든다.
카드는 코드를 읽고 쓰고, 줄마다 `파일:줄`을 단다.

## 카드 예시 (요구사항 커밋마다)

```markdown
## R3 — 음성 업로드 분석 (커밋 a1b2c3d)

- 실패·timeout: 모델 응답 quote가 원문에 없으면 1회 재요청, 또 없으면 그 항목을 버리고 빈 issues로 200 반환. 화면은 "고칠 점 없음"과 구분 안 됨 (app/analyze.py:80-93, static/app.js:63)
- 동시 요청: async 핸들러 안에서 동기 SDK 호출 → 호출 중 이벤트 루프 막힘, 다른 요청 대기 (app/main.py:55, app/llm.py:18)
- 데이터가 남는 곳: 요청 본문 전체를 메모리에 올린 뒤 10MB 검사 → 제한이 메모리를 막지 못함. 프런트 chunks 배열은 다음 녹음 시작 전까지 남음 (app/main.py:48-52, static/app.js:5)
- 테스트 범위: test_R3_S1은 B3 존재와 quote에 '환불' 포함만 검사 → 다른 문장이 quote에 섞여도 통과 (tests/test_r3.py:33-37)
- 결정 주체: 사과만으로는 공감 아님 = [결정] 내 판단 (담당자는 기준 없다고 답함 #4-2)
```

## 규칙
- 네 영역(실패·timeout / 동시 요청 / 데이터가 남는 곳 / 테스트 범위)은 항상 쓴다. 해당 없으면 `해당 없음 (이유)`로 한 줄.
- "결정 주체"는 이번 변경에 `[결정]`이나 이전과 바뀐 기준이 있을 때만 쓴다. 담당자 확정과 내 판단을 섞지 않는다.
- 동작은 순서대로 쓴다: 조건 → 몇 번 → 무엇을 반환 → 화면에 무엇이 보이나.
- "충분하다", "보장한다"는 쓰지 않는다. 막는 것과 막지 못하는 것을 나눠 쓴다.
- 뒤 커밋이 앞 카드의 동작을 바꾸면 앞 카드를 고친다. 지난 동작을 남겨 두지 않는다.
- 한 카드는 5~6줄을 넘기지 않는다. 제출 직전에 전체를 5분 안에 다시 읽을 수 있어야 한다.
