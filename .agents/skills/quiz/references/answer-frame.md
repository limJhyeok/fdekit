# 답안 틀: 라벨 붙인 4칸 (판단형이면 판단 한 줄을 앞에)

시간이 부족해 완성된 문장으로 쓰기 어려우므로 **라벨 + 짧은 구절** 형태로, 명사 위주로 쓴다.
칸 순서는 항상 **사실 → 이유 → 한계·영향 → 대응**이다.

## 질문 종류에 따라 첫 줄이 다르다

| 질문 종류 | 알아보는 법 | 첫 줄 |
|---|---|---|
| 판단형 | "~으로 충분한가?", "~해도 되는가?", "~이 맞는가?" | **질문 말을 받아** 판단을 쓴다. `충분한가: 아니오 — 한 줄 이유`. 그다음 4칸 |
| 설명형 | "~한 이유와 영향은?", "~하면 어떻게 되나?" | 판단 줄 없이 바로 `사실:` |

- 판단형에서 판단 줄을 앞에 두는 이유: 그 줄이 질문에 대한 답이다. 뒤에 두면 시간 초과 자동 제출 때 가장 먼저 잘리고, 채점자는 4칸을 다 읽은 뒤에야 답을 안다.
- `결론:`이라고 쓰지 않는다. 질문이 묻지 않은 판단을 앞세운 것처럼 읽힌다. 질문의 말(`충분한가:`, `되는가:`)로 시작해 질문에 답하는 줄임을 드러낸다.
- 설명형 질문에 판단 줄을 억지로 만들지 않는다. "누락값을 제외한 이유는?"에 `결론: 제외가 맞음`을 쓰면 묻지 않은 것에 답한 줄이 된다.
- 끝에 `요약:` 한 줄은 선택이다. 4:40 전에 시간이 남을 때만 쓴다. 없어도 감점하지 않는다.

## 라벨 규칙
채점자는 이 틀을 모른다. ①②③④ 같은 번호만 쓰면 어느 줄이 어느 하위 질문의 답인지 채점자가 추측해야 하고, 잘못 짝지으면 답한 것도 안 한 것으로 본다.
- **줄 앞에 라벨을 단다.** 기본 라벨은 `사실:` `이유:` `한계·영향:` `대응:`.
- **질문에 나온 단어가 있으면 그 단어를 라벨로 쓴다.** 질문이 "제외한 이유와 매출 집계에 미치는 영향은?"이면 `이유:` `매출 집계 영향:`. "실패하면 사용자는 무엇을 보나?"면 사실 칸 라벨을 `실패 시 화면:`으로.
- **순서는 바꾸지 않는다.** 어느 줄이 무엇의 답인지는 라벨이 알려 주므로 질문에 맞춰 순서를 바꿀 필요가 없다. 사실 → 이유 → 한계·영향 → 대응은 그 자체로 읽기 쉬운 흐름이고, 시간에 쫓길 때 문항마다 순서를 정하지 않아도 된다.
- **인과는 말로 쓴다.** `→`는 순서·흐름(감지 → 안내 → 복구)에만 쓰고, 원인과 결론은 `~므로`, `~면`으로 쓴다. `왜곡 → 대체 안 함`은 "왜곡돼서 안 했다"인지 "안 해서 왜곡됐다"인지 읽는 사람이 정해야 한다.
- 라벨 4개를 다는 데 10초 남짓이 든다. 시간 배분은 바뀌지 않는다.

## 칸

| 칸 (기본 라벨) | 쓸 것 | answer-key 칸 | 앱 리허설 채점 단계 |
|---|---|---|---|
| 사실 | 무엇을 했나 / 무엇이 일어나나 (위치·조건·숫자 중심) | `fact` | weak_point |
| 이유 | 근거 출처(담당자 합의, 요구사항, 내 판단, 기술 제약) + 버린 대안 | `reason` | (weak_point·impact 보조) |
| 한계·영향 | 이 선택이 깨지는 조건과, 그때 누구에게 어떤 결과가 생기나 | `impact` | impact |
| 대응 | 유지할 것 / 바꿀 것 / 확인 방법(입력 → 기대 결과) | `plan` | plan |

## 유형별 4칸 채우기

`type`은 answer-key.json에 쓰는 값이다. "—"는 그 유형에서 생략해도 감점하지 않는 칸이다.

| 유형 (`type`) | 사실 | 이유 | 한계·영향 | 대응 |
|---|---|---|---|---|
| 왜 이렇게 만들었나 (`design_reason`) | 선택한 방식 | 근거 출처 + 대안 대비 장점 | 그 선택의 비용·약점 | 유지할 제약 + 개선 |
| 장애가 나면 (`failure_response`) | 실패 시 실제 동작 순서(재시도 횟수, 응답, 화면) | — (생략 가능) | 사용자가 무엇을 오해·손실하나 | 감지 → 사용자 안내 → 복구 → 재발 방지 테스트 |
| 위험 예측: 동시성·부하·입력 (`risk_prediction`) | 병목 지점과 그 메커니즘 | — | 어느 조건에서 터지나 | 완화책 + 재현 방법 |
| 요구사항 ↔ 구현·테스트 (`requirement_mapping`) | 요구 원문 vs 실제 검사 범위의 차이 | — | 테스트는 통과하지만 틀리는 사례 | 빠진 검사 1개 |
| 데이터 흐름·보관 (`data_flow`) | 어디에 생기고, 어디에 남고, 언제 지워지나 | 보관 제약의 출처 | 남는 곳과 그 위험 | 정리 시점 + 확인 방법 |
| 결정 변경 이력 (`decision_change`) | 이전 → 이후 | 담당자 확정 vs 내 판단 구분 | 이전 해석을 유지했다면 생길 문제 | 회귀 사례 + 기대 판정 |
| 데이터 처리 결정: 결측·이상치·필터 (`data_handling`) | 몇 건/몇 %를 어떻게 처리했나 | 근거 출처 | 집계·지표가 어느 방향으로 왜 왜곡되나 | 처리 전후 비교 + 리포트에 표기 |

AI 제안을 받아들이거나 거절한 근거를 묻는 질문은 `design_reason`으로 낸다. 이유 칸에 "AI 제안 → 받아들인/거절한 근거"를 쓴다.

## 예시: "누락값을 제외한 이유와 매출 집계에 미치는 영향은?"

설명형 질문이라 판단 줄 없이 사실부터 쓴다. 질문이 묻는 이유와 영향은 라벨에 질문 단어를 쓴다.

```
사실: 금액 결측 412건(3.1%) 집계에서 제외 (clean.py dropna)
이유: 담당자 "금액 없는 건 취소 주문" → 매출 아님. 0으로 채우면 평균 단가가 왜곡되므로 대체 안 함
매출 집계 영향: 취소가 아닌 결측이 섞여 있으면 총매출 과소 집계. 특정 지점·기간에 몰려 있으면 비교 지표 편향
대응: 제외 건수·기간 분포 리포트 표기, 포함/제외 합계 비교. 결측 몰린 구간은 담당자 재확인
```

번호만 쓴 답(아래)은 내용이 같아도, 채점자가 어느 줄이 "영향"인지, `→`가 원인인지 결과인지 스스로 판단해야 한다.

```
① 금액 결측 412건(3.1%)을 집계에서 제외 (clean.py dropna)
② 담당자 답변: "금액 없는 건 취소 주문" → 매출 아님. 0으로 채우면 평균 단가 왜곡 → 대체 안 함
③ ...
```

## 예시 (판단형): "업로드 크기 제한 50MB로 충분한가? 동시 업로드 시 영향은?"

```
충분한가: 아니오 — 크기 검사가 본문을 다 읽은 뒤에 일어남
사실: 50MB 초과면 413 응답, 검사는 본문 전체를 읽은 뒤 (upload.py:46)
이유: 담당자 기준은 "보통 30분 녹음"(#3-2)뿐, 50MB는 내 판단(D4)
동시 업로드 영향: 큰 요청이 검사 전에 메모리에 올라가므로, 동시에 오면 메모리 부족 → 다른 사용자 요청까지 지연
대응: 50MB 유지, 검사를 Content-Length 확인으로 앞당김. 확인: 60MB 요청 → 즉시 413, 메모리 증가 없음
```

## 문항당 5분 시간 배분

| 구간 | 시간 | 할 일 |
|---|---|---|
| 분해 | 0:00 – 0:40 | 판단형인지 설명형인지 가르고, 하위 질문을 나눠 **라벨을 질문 단어로 정한다**. "충분한가?"류 함정 표현 표시 |
| 판단 | 0:40 – 1:00 | 판단형만: `충분한가: 아니오 — 한 줄 이유`. 설명형은 건너뛰고 본문에 시간을 쓴다 |
| 본문 | 1:00 – 4:00 | 사실 → 이유 → 한계·영향 → 대응 (칸마다 2~3줄) |
| 점검 | 4:00 – 4:40 | 하위 질문마다 라벨 붙은 줄이 있는지, 숫자·함수명·화면 문구가 들어갔는지 |
| 여유 | 4:40 이후 | (선택) `요약:` 한 줄. 제출. 시간 초과 자동 제출에 대비해 최소 20초 남긴다 |
