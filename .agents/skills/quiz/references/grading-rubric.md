# 채점과 해설

문장력이 아니라 내용을 채점한다. 라벨 + 짧은 구절 답안이 정상이다.
(`prompts/rehearsal_grade.md`의 기준을 4칸으로 넓힌 것이다.)
이 기준은 4칸 틀과 모범 답안을 아는 채점이라 실전 채점자보다 너그럽다. 그래서 범용 채점(`generic-grade-prompt.md`)을 따로 돌려 형식 손해를 잡는다.

칸 판정은 라벨이 아니라 **내용**으로 한다. 라벨이 없거나 틀려도 그 칸의 내용이 있으면 판정하고, 라벨 문제는 형식 점검에 기록한다.

## 칸별 판정

| 판정 | 뜻 |
|---|---|
| met | 정확히 짚음. 위치(파일·함수·화면 요소)나 조건·숫자가 들어 있음 |
| partial | 방향은 맞으나 모호하거나 일부만. 예: "에러 처리가 약함"(어디인지 없음) |
| missed | 없음, 틀림, 또는 일반론만 |
| 해당 없음 | answer-key의 `optional_cells`에 있고 사용자도 비워 둠. 썼다면 met/partial/missed로 판정 |

- 모범 답안과 다른 약점·이유를 짚었어도 실제 코드·기록에 있고 타당하면 met. 확인한 좌표를 해설에 단다.
- 대응: "어디를 보고 무엇으로 확인하겠다"를 정확히 말하면 partial 이상. 확인 방법에 입력 → 기대 결과까지 있으면 met.
- 이유: 근거 출처를 틀리게 말하면(내 판단을 담당자 합의라고 함) partial 이하. 실전에서 가장 위험한 실수다.
- 판단 줄: 판단형 질문(`conclusion`이 있음)인데 판단 줄이 없거나 반대면 해설에서 반드시 짚는다. 칸 판정과 별도로 기록한다.
- 설명형 질문(`conclusion`이 null)에서는 판단 줄이 없어도 감점하지 않는다. 묻지 않은 판단을 `결론:`으로 앞세웠으면 형식 점검에 적는다.
- 끝의 `요약:` 줄은 있어도 없어도 판정에 영향이 없다.

## 형식 점검 (칸 판정과 따로)

| 항목 | 기준 |
|---|---|
| 판단 줄 | 판단형: 첫 줄에 질문 말로 시작하는 판단이 있음(`충분한가: 아니오 — …`). 설명형: 해당 없음 |
| 라벨 | 하위 질문마다 라벨 붙은 줄이 있음. 질문 단어를 라벨로 썼는지. 사실 → 이유 → 한계·영향 → 대응 순서인지 |
| 화살표 | 원인·결론을 `→`만으로 이은 곳이 있으면 인용 |
| 하위 질문 | `sub_questions`를 모두 다룸. 빠진 것 이름 |
| 구체어 | `must_mention` 중 몇 개가 나왔나 (예: 2/3) |
| 시간 | 4:40 이하 / 5:00 이하 / 초과 |
| 범용 채점 | 하위 질문별 answered / unclear / not_answered, 형식 손해 여부 (`generic-grade-prompt.md`의 비교표) |

## 잘못 이해한 것 (misconception)
- 사용자 답이 코드와 다르게 말한 부분. 해당 코드 줄을 읽어 확인한 것만 쓴다.
- "그렇게 동작하지 않음"이 아니라 "실제로는 `retry=2`라서 세 번 호출됨 (`llm.py:31`)"처럼 사실로 쓴다.

## 해설 형식 (문항마다)

```
### Q3 — 사실 met · 이유 partial · 한계·영향 missed · 대응 partial · 3:52
질문: 업로드 크기 제한 50MB로 충분한가? 동시 업로드 시 영향은? (판단형)
판단 줄: ✔ / 하위 질문: 2/2 / 구체어: 1/3 (빠짐: MAX_UPLOAD_MB, "처리 중..." 문구)
범용 채점: 6/10, "허용 기준의 근거" answered · "동시 업로드 시 영향" unclear → 형식 손해 1

이유 — partial
  사용자: "담당자가 정함"
  실제: 50MB 제한은 담당자 말이 아니라 내 판단(DECISIONS.md D4). 담당자는 "보통 30분 녹음"(#3-2)이라고만 함
  → 실전에서는 "담당자 30분 녹음 기준 → 내가 50MB로 정함"으로 구분해 쓴다

한계·영향 — missed
  app/upload.py:40-52
  <코드 5~15줄>
  크기 검사가 본문을 다 읽은 뒤(46행)라서, 큰 요청은 검사 전에 메모리에 올라감 → 동시 업로드 시 서버 메모리 부족

형식 손해 — "동시 업로드 시 영향"
  범용 채점자: "③ 메모리 → 느려짐"이 영향인지 대응인지 알 수 없음 (unclear)
  원인: 번호만 있고 라벨 없음, 원인과 결과를 → 로만 이음
  고친 줄: "동시 업로드 영향: 메모리가 차므로 다른 사용자 요청까지 느려짐"

고쳐 쓴 답안:
  충분한가: 아니오 — 크기 검사 시점이 늦음
  사실: ...(사용자 답 유지)
  이유: 담당자 기준은 30분 녹음(#3-2)뿐, 50MB는 내 판단(D4)
  동시 업로드 영향: 본문 전체를 읽은 뒤 검사하므로(upload.py:46) 큰 요청이 동시에 오면 메모리 부족, 전체 사용자 영향
  대응: ...(사용자 답 + 빠진 확인 방법: 60MB 요청 → 413, 메모리 증가 없음)
```

- met 칸은 한 줄로 넘어간다. 코드를 붙이지 않는다.
- 고쳐 쓴 답안은 사용자 표현을 최대한 살리고 빠진 칸만 채운다. 라벨은 질문 단어로, 순서는 사실 → 이유 → 한계·영향 → 대응, 판단형이면 판단 줄을 맨 앞에(`answer-frame.md`). 실전에서 쓸 수 있는 길이(칸마다 2~3줄)로.
- 형식 손해 절은 범용 채점에서 형식 손해가 난 하위 질문에만 쓴다.
