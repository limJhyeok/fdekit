# Requirements Alignment: 답변 반영 → 요구사항 → 범위 합의

현업과 주고받은 대화를 근거로 요구사항을 확정하고 범위를 합의한다.
에이전트는 메시지를 직접 보내지 않는다. 사용자가 답변을 붙여 넣으면 반영하고, 다음에 보낼 메시지 초안을 만든다.

## 범위
- 하지 않는 것: 기술 스택 선택, 설계, 구현. 메시지 발송.
- 메시지 언어는 담당자의 기술 배경에 맞춘다. 기본은 기술 용어를 쓰지 않고 기술 선택도 묻지 않는 것이며, 담당자가 개발자임이 [사실]로 드러난 경우만 예외다(`../problem-discovery/references/message-template.md`의 '담당자에 맞춘 언어').
- 다루는 파일(작업 디렉터리 기준)
  - `conversation-log.md` — 대화 원문 기록 (새로 만들거나 이어 씀)
  - `problem-notes.md` — 갱신
  - `partner-message.md` — 다음 차수 메시지 초안으로 갱신
  - `requirements.md` — 요구사항 목록, 범위 제안, 합의 기록

## 매 차수 반복 (답변을 받을 때마다)

### 1. 대화를 원문 그대로 기록
`references/templates.md`의 대화 기록 형식으로 `conversation-log.md`에 추가한다.
- 보낸 메시지와 받은 답변을 **고치지 않고** 그대로 옮긴다. 요약하지 않는다.
- 보낸 메시지는 첫 차수에만 "초안대로 보냈는지" 사용자에게 한 번 묻는다. 이후로는 사용자가 따로 말하지 않으면 초안대로 보낸 것으로 기록하고, 같은 안내를 기록에 반복하지 않는다.
- 차수와 문단마다 번호를 붙인다(예: `#2-1`). 이 번호가 이후 모든 근거 표시의 출처가 된다.

### 2. 답변 판정
보낸 질문마다 판정한다.

| 판정 | 기준 | 다음 행동 |
|---|---|---|
| 답함 | 구현에 쓸 수 있을 만큼 구체적 | 노트 반영 |
| 일부 답함 | 방향은 있으나 기준·예외·수치가 빠짐 | 빠진 부분만 후속 질문 |
| 답 없음 | 언급 없음, 다른 이야기로 넘어감 | 질문을 바꿔 다시 묻기(해석 확인 또는 사례 방식으로) |
| 모름 | 담당자도 모른다고 함 | 기본 가정을 쓰고, 노트에 "담당자 미확정"으로 기록 |

- **범위가 좁혀진 답**을 찾는다. "그 사례에서는", "이번에는", "그 고객은"처럼 답이 특정 사례·상황에 묶여 있으면, 판정이 '답함'이어도 **일반화 질문**("평소 다른 <상황>에서도 같은가요? 그 밖에 자주 보시는 점이 있나요?")을 다음 차수에 반드시 넣는다. 질문을 사례로 물었다면 답도 사례에 묶이기 쉽다.
- 답변에 **질문하지 않은 새 정보**가 있으면 따로 표시한다. 새 질문 거리가 되는 경우가 많다.
- 답변이 자료(문서·데이터)와 다르면 "자료: <값> / 담당자: <값>"으로 나란히 적는다. 어느 쪽이 현재 유효한지 담당자가 분명히 말하지 않았으면 확인 질문을 만든다.

### 3. 노트 갱신
- 답을 받은 [가설]·[추정]은 [사실]로 올리고 출처를 `대화 #n-m`으로 단다.
- 답변이 기본 가정과 다르면 가정을 지우고, 다르다는 사실을 한 줄 남긴다.
- 노트의 한 질문이 두 가지 이상을 묻고 있었는데 메시지나 답에서 한쪽이 빠졌으면, 빠진 쪽을 질문 리스트에 따로 남긴다. 판정표의 '빠짐' 메모를 다음 차수 질문으로 반드시 옮긴다.
- 새로 생긴 의문은 질문 리스트에 추가한다. 질문 방식(열린 질문/해석 확인/값 인용/사례)도 함께 정한다.
- 답변을 근거로 새 [추정]을 만들 때도 `problem-discovery`의 자기 검토 체크리스트(`../problem-discovery/references/self-review.md`)를 적용한다. 담당자의 말을 넓혀 해석하거나 빈도를 과장하지 않는다.

### 4. 다음 메시지 초안
`partner-message.md`를 다음 차수 메시지로 갱신한다.
- 우선순위: 일반화 질문·빠진 부분 재질문 → 아직 답이 없는 **요청 핵심 표현**과 **과제의 핵심 동작** 질문 → 새 정보에서 생긴 질문 → 계획된 다음 차수 질문
- "정해 둔 기준이 없어요"류 답이 두 번 이어지면 그 주제는 기본 가정으로 닫고, 핵심 동작 쪽으로 주제를 바꾼다.
- 한 번에 1~3개. 작성 규칙은 `../problem-discovery/references/message-template.md`를 따른다.
- 후속 질문 패턴은 `references/followup-patterns.md`를 참고한다.

## 정리 단계 (질문을 마무리할 때)

### 5. 이해 확인 메시지
핵심 질문(사용자·사용 장면, 업무 기준, 우선순위, 제약)에 답을 받았으면, 이해한 내용을 정리해 확인을 구한다.
- 번호를 붙인 짧은 문장 5~8개. 각 문장은 대화에서 들은 내용만 담는다.
- **담당자의 표현을 바꾸지 않는다.** 핵심 단어는 원문 그대로 쓴다(예: "확인해서 말씀드려야 한다"를 "확인 중"으로 바꾸지 않는다).
- 확인 문장이나 해석 확인 질문에 **대화에 나온 적 없는 예시를 넣지 않는다.** 새 예시가 기준의 범위를 바꿀 수 있다(예: '보상' 기준을 확인하면서 '방 변경'을 예로 들면, 담당자가 구분하는 두 범주를 섞게 된다). 새 예시가 필요하면 별도 질문으로 묻는다.
- "틀린 부분만 알려 주세요"로 끝내 답하기 쉽게 한다.
- 담당자가 고친 부분은 대화 기록과 노트에 반영한다.

### 6. 요구사항 목록
`references/templates.md`의 요구사항 형식으로 `requirements.md`를 쓴다.
- 요구사항은 **사용자가 할 수 있어야 하는 일**로 쓴다. 기술 구현으로 쓰지 않는다.
- 모든 요구사항에 근거(`대화 #n-m` 또는 문서·항목)를 단다. 근거가 없으면 요구사항이 아니라 제안이다. 제안은 따로 모은다.
- 중요도
  - **필수:** 없으면 담당자가 말한 문제가 해결되지 않음, 또는 담당자가 "꼭"이라고 함
  - **권장:** 있으면 좋다고 함, 또는 필수의 품질을 높임
  - **이후:** 이번 범위 밖으로 미뤄도 핵심 문제는 해결됨
- 요구사항마다 **확인 방법**을 한 줄 적는다(예: "문서에 없는 질문을 했을 때 '확인 필요'로 안내되는지"). 나중에 시연·테스트 기준이 된다.
- 기능의 성공 기준은 관련 R-ID의 확인 방법에, 여러 기능에 걸친 결과 품질·속도 같은 기준은 B-ID에 적는다. 실행 환경·제출 형식처럼 반드시 지켜야 할 제한은 C-ID에 적는다. 같은 기준을 중복해서 만들지 말고 관련 ID를 연결한다.
- 기준마다 담당자가 관찰할 수 있는 합격 조건과 확인 방법을 적는다. 수치 기준이면 대상 입력·실행 환경·측정 방식·합격선을 확인한다. 담당자가 정하지 않은 수치나 평가 방법을 합의된 기준으로 채우지 않는다. 핵심 기준이 모호하면 후속 질문으로 묻고, 시간상 답을 못 받으면 기본 가정 또는 미확인으로 표시한다.

### 7. 범위 제안과 합의
남은 시간과 제약을 기준으로 범위를 제안하는 메시지를 쓴다. 형식은 `references/followup-patterns.md`의 범위 제안을 따른다.
- 이번에 할 것 / 이번에 하지 않을 것을 나누고, **하지 않는 이유**를 담당자가 이해할 수 있는 언어로 적는다(기본은 업무 언어). 이번 범위의 R-ID에 적용할 B-ID와 C-ID, 제안한 합격 조건도 함께 확인한다.
- 필수를 빼야 한다면 그 사실과 대안을 분명히 말한다.
- 담당자가 아쉬움을 보이거나 빠진 필수를 짚으면 조정안을 다시 제안한다.
- 담당자가 우선순위를 정하지 못하면, 대화 근거(가장 많은 문의, 가장 곤란한 실수 등)를 들어 먼저 제안한다.
- **합의 문장을 원문 그대로** `requirements.md`의 합의 기록에 남긴다. 명시적 동의("좋아요, 그렇게 진행해 주세요" 같은 문장)가 없으면 합의된 것으로 보지 않는다.

## 질문을 멈출 때

### 시간 예산
- 기준 시간은 **사용자가 알려 준 실제 작업 시간**이다. 문제 설명의 시간과 다르면 사용자 쪽을 쓰고, 노트·요구사항의 제약에 둘 다 적는다(예: "문제 설명 4시간 / 실제 3시간(사용자 안내)").
- 질문·합의에 쓸 시간 상한을 처음에 분 단위로 계산해 노트에 적는다. 전체의 15~20%다(180분이면 27~36분).
- 시간은 타이머를 보는 사용자가 판단한다. 에이전트는 경과 시간을 추측하거나 기록하지 않는다. 사용자가 "시간이 다 됐다"거나 남은 시간을 알려 주면 그에 따른다.

### 멈추기 전 점검 (모두 통과해야 멈춘다)
1. **요청 핵심 표현 점검:** 현업 요청 인용문의 핵심 표현마다 답을 하나 이상 받았다. 예: "말해 보고", "고칠 점", "코칭 방식", "부담 없이"처럼 요청을 이루는 표현을 노트에서 뽑아, 표현별로 근거가 된 대화 번호를 적는다. 빈 표현이 있으면 그것부터 묻는다.
2. **핵심 동작 점검:** 과제의 핵심 동작(무엇을 입력받고, 무엇을 판단·분석하고, 결과를 어떻게 보여 주는지)에 대해 담당자의 기준을 들었다. 운영 정책(보관, 열람 권한 등) 답만으로는 통과하지 않는다.
3. **일반화 점검:** 업무 기준이 사례 하나에서만 나왔다면, 다른 상황에서도 같은지 확인했다.

### 멈춰도 되는 경우
- 위 점검을 모두 통과했다.
- 또는 사용자가 시간 상한에 닿았다고 알려 줬다. 이때는 점검에서 빈 항목을 기본 가정으로 처리하고, 노트와 요구사항에 "미확인"으로 표시한다.
- "최근 두 차수에서 새 정보가 없다"는 그것만으로 멈출 이유가 되지 않는다. 주제를 바꿔 위 점검의 빈 항목을 묻는다.

## 사용자에게 보고 (매 차수)
- 이번 답변에서 확정된 것, 기본 가정과 달랐던 것
- 아직 열린 핵심 질문
- 다음 메시지 초안 위치(`partner-message.md`)
- 노트에 적은 시간 상한(분). 사용자가 타이머와 비교해 계속할지 정한다
- 범위 합의가 끝났으면 `build-from-requirements` 스킬로 이어 간다는 점
- 멈추기 전 점검 3가지의 현재 상태와, 정리 단계로 넘어갈 시점인지에 대한 판단
