# Write Handoff: 다음 사람이 바로 이어서 작업하게

HANDOFF.md는 "지금 어디까지 왔고, 무엇을 지켜야 하고, 무엇이 위험한가"를 모은 문서다. architecture.md는 다음 개발자가 실제 코드를 따라갈 수 있도록 현재 시스템의 구성·흐름·경계를 설명한다. 두 파일을 프로젝트 루트에 저장한다.
원칙은 하나다. **다음 사람이 담당자에게 다시 묻거나, 이미 겪은 실수를 반복하지 않게 한다.**

- 실행 방법·기능 대응표는 README에 둔다. HANDOFF는 README에 링크하고 내용을 되풀이하지 않는다.
- 구성요소와 흐름의 상세 설명은 architecture.md에 둔다. HANDOFF에는 이어서 작업할 때 필요한 핵심 진입점과 architecture.md 링크만 남긴다.
- 결정의 이유는 DECISIONS.md, 담당자 말은 conversation-log.md에 있다. HANDOFF는 **근거 번호로 가리키고 요약만** 한다.
- 쓰는 시점: build-from-requirements 6단계(문서·제출). 180분 과제 기준 **10분 안팎**. 그래서 작업 중에 겪은 일(정정받은 것, 깨진 테스트, 환경 사고)은 그때그때 한 줄씩 메모해 둔다.

## 시작 전
- 입력: 프로젝트에 있는 요구사항·결정·검증·운영 문서, 코드와 설정, 테스트, `git log`. 예: `requirements.md`, `conversation-log.md`, `ACCEPTANCE.md`, `DECISIONS.md`, `problem-notes.md`, `partner-message.md`, `README.md`.
- `git status`, `git log --oneline -20`으로 기준 커밋을 정한다. **다른 세션이 같은 폴더를 고치고 있지 않은지** 이때 확인한다.
- 형식은 `references/handoff-template.md`를 따른다. 과제에 해당하지 않는 칸은 지우지 말고 "해당 없음(이유)"으로 둔다.

## architecture.md 작성·저장
- `references/architecture-guide.md`를 읽고 실제 프로젝트의 형태에 맞게 작성한다.
- 실행 진입점에서 출발해 구성요소, 주요 기능의 흐름, 데이터·상태가 저장되거나 외부로 나가는 경계, 핵심 검증·오류 경로를 코드·설정·테스트와 대조한다. 확인하지 못한 동작은 추정이라고 표시한다.
- 프로젝트에서 의미 있는 전체 구성 그림과 주요 흐름 그림을 포함한다. 다이어그램 방식은 저장소의 미리보기 환경에 맞게 고르고, 렌더링이 필요한 형식을 쓰면 일반 Markdown에서도 이해할 수 있는 텍스트 설명을 함께 둔다.
- 기존 architecture.md가 있으면 현재 코드와 대조해 갱신한다. HANDOFF를 쓰기 전에 프로젝트 루트의 architecture.md로 저장하고, HANDOFF의 구조 절에서 링크한다.

## 1. 사실 모으기 (도구로 확인)
문서에 들어갈 숫자·상태는 기억으로 쓰지 않는다. 도구로 확인한 값만 쓴다.

| 항목 | 확인 방법 |
|---|---|
| 기준 커밋 | `git rev-parse --short HEAD` |
| 구현·확인된 요구사항 | ACCEPTANCE.md '확인 결과 기록'과 테스트 결과. 기록과 실제가 다르면 기록을 먼저 고친다 |
| 테스트 개수·시간·비용 | 전체 테스트를 실제로 실행한 출력. LLM·외부 API를 부르는 테스트는 호출 횟수도 센다 |
| "건너뜀" 테스트 | 키가 없어 건너뛴 테스트가 있으면 통과로 세지 않는다 |
| 의존성 버전 | `pip show`, `npm ls` 등 실제 설치된 버전 |
| 외부 API 호출 제약 | 직접 호출해 본 결과만. 날짜를 붙인다 |
| 파일 역할 | 실제 파일 목록(`git ls-files`)과 대조 |

## 2. 항목별로 쓰기
`references/handoff-template.md`의 6개 절을 채운다. 절마다 지킬 것:

1. **현재 개발 범위** — 한 문단 요약(업무 언어로), 구현된 요구사항 표(ID ↔ 시나리오 ID), architecture.md 링크와 다음 작업에 필요한 진입점·파일 역할 요약. 판정·업무 기준이 들어 있는 파일은 굵게 표시한다. "다 됨"이 아니라 **확인된 것만** 넣는다.
2. **앞으로 추가될 수 있는 범위** — 합의되지 않은 것만. 칸: 후보 / 지금까지 담당자 말(원문 인용 + `#n-m`) / 협의할 점 / 영향(바뀌는 파일, 판정이 바뀔 수 있는 테스트, 부딪치는 제약 ID). 첫 줄에 "합의 전에는 만들지 않는다"를 적는다.
3. **아직 확인되지 않은 내용** — 세 가지로 나눈다.
   - 3-1 담당자 기준이 없어 작업자가 정한 것: 담당자에게 **알림 여부와 동의 여부를 구분**해 쓴다("알렸고 반대는 없었지만 동의받은 것은 아님", "알리지 않음", "기술적 결정").
   - 3-2 담당자 쪽에서 확인이 필요한 사항: **담당자가 쓴 표현 그대로** 쓴다. 정정받은 적이 있으면 그 사실과 다음 사람이 쓸 표현을 적는다.
   - 3-3 아직 묻지 않은 질문: 질문 리스트의 Q 번호.
4. **버그 가능성·취약성** — `references/risk-checklist.md`로 찾는다. 칸: 심각도 / 내용 / 확인 여부 / 고치는 방향. 동작·성능과 보안·운영을 나눈다. 심각도 높은 것부터.
5. **반드시 지킬 제약** — 담당자와 합의한 제약(ID / 제약 / 근거 / 코드에서 지키는 방법 / 확인하는 테스트)과 과제·환경 제약을 나눈다. "지키는 방법"에는 **하면 안 되는 구현**을 구체적으로 쓴다(예: "업로드를 임시 파일로 받는 방식 금지: 크기가 크면 디스크에 씀").
6. **기타** — 기준을 바꿀 때의 순서, 테스트 실행법, 담당자와 소통할 때, 작업 환경 주의. **실제로 겪은 사례**가 있는 것만 쓴다. 일반론은 넣지 않는다.

## 3. 버그 가능성 찾기
- 작성한 에이전트 혼자 찾으면 자기가 만든 가정을 그대로 통과시킨다. 시간이 되면 새 컨텍스트 서브에이전트에게 `references/risk-checklist.md`와 코드 경로만 넘기고, 찾은 것을 받는다. 내 결론은 전하지 않는다.
- 각 항목의 **확인 여부**를 정직하게 단다.

| 표시 | 뜻 |
|---|---|
| 재현함 | 실제로 일으켜 봄. 어떻게 재현했는지 한 줄 (예: "2초짜리 가짜 요청 두 개 동시 → 2.3초·4.3초") |
| 코드 확인 | 코드를 읽어 확인, 실행은 안 함 |
| 부분 확인 | 일부 조건에서만 확인 (무엇이 빠졌는지 적음) |
| 테스트에서는 발생 안 함 | 가능성은 있으나 지금 테스트로는 못 봄 |
| 설계 | 알고 택한 동작 |

- 재현하는 데 1~2분이면 되는 높은 심각도 항목은 재현해 본다. 고치지는 않는다(제출 직전 코드 변경은 위험). 고칠 시간이 있으면 사용자에게 묻는다.

## 4. 자기 검토
저장 전에 `references/self-review.md`의 패턴에 걸리는 문장이 없는지 본다. 특히:
- 담당자 말을 넓히거나 바꿔 쓰지 않았는가 (근거 번호의 원문과 나란히 놓고 본다)
- 합의되지 않은 것을 1절(현재 범위)에, 작업자가 정한 것을 합의로 쓰지 않았는가
- 문서에 적은 파일·함수·환경변수·테스트 이름이 실제로 있는가 (`grep`으로 확인)
- architecture.md의 구성·흐름·외부 경계가 현재 코드와 일치하는가. HANDOFF의 구조 요약이 architecture.md와 충돌하지 않는가
- 링크한 문서가 모두 있고, HANDOFF에서 architecture.md로, README에서 HANDOFF.md로 링크되는가
- partner-message.md의 "보낼 메시지/기다리는 답" 상태와 HANDOFF 6절이 맞는가

## 사용자에게 보고
- 기준 커밋과 HANDOFF.md·architecture.md 경로
- 새로 재현한 버그(있으면)와 고칠지 여부 판단 요청
- 쓰다가 발견한 문서·코드 불일치(고친 것 / 남긴 것)
- 커밋은 사용자가 요청할 때만 한다
