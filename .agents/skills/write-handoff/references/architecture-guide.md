# architecture.md 작성 가이드

목적: 다음 개발자가 코드를 처음 열었을 때 시스템의 주요 부분과 흐름을 찾아가고, 변경할 때 어느 경계를 확인해야 하는지 알 수 있게 한다. 이 문서는 현재 구현을 설명한다. 설계 의도·과거 결정은 결정 기록으로, 미해결 위험과 후속 작업은 HANDOFF로 연결한다.

## 근거를 모으는 순서

1. 저장소의 실행·빌드·배포 진입점과 설정을 찾는다. 프로젝트가 웹 서버, CLI, 라이브러리, 배치, 이벤트 소비자, 모바일 앱, 다중 서비스 중 무엇인지 실제 파일로 확인한다.
2. 주요 기능 하나가 입력에서 결과까지 지나가는 경로를 코드에서 추적한다. 호출되는 모듈, 프로세스 또는 서비스, 데이터 변환, 저장·외부 전송, 실패 시 동작을 확인한다. 기능마다 경로가 다르면 대표 흐름을 추가한다.
3. 테스트와 운영 문서로 경계를 교차 확인한다. 문서와 코드가 다르면 현재 동작을 코드 기준으로 쓰고 불일치를 HANDOFF에 남긴다. 실행하지 않은 경로는 실행 검증을 했다고 쓰지 않는다.

## 문서에 담을 내용

프로젝트에 해당하는 항목을 골라 설명한다. 없는 계층이나 서비스를 채우기 위해 가상 구성요소를 만들지 않는다.

- 시스템의 목적과 범위: 누가 무엇을 실행하거나 요청하고 어떤 결과를 받는지.
- 실행 형태와 환경: 시작 명령, 진입점, 주요 프로세스·서비스, 필요한 설정, 초기화와 종료. 배포 구성이 있으면 코드에서 확인한 범위만.
- 구성요소와 책임: 모듈·패키지·서비스·저장소 등 중요한 경계와 실제 파일 경로. 단순 파일 목록보다 연결 관계를 우선한다.
- 주요 흐름: 요청·명령·이벤트·작업 중 프로젝트에 맞는 입력에서 출력까지의 순서. 핵심 분기와 실패 경로를 포함한다.
- 데이터와 상태: 입력 검증, 변환, 저장 위치와 수명, 외부 시스템으로 나가는 데이터, 권한·신뢰 경계. 해당하면 동시성·재시도·시간 제한도 설명한다.
- 결과 검증과 오류 처리: 외부 응답이나 내부 계산 결과를 어디서 어떤 조건으로 검사하는지, 실패가 호출자에게 어떻게 전달되는지. 형식 검증과 업무 의미 검증을 구분한다.
- 현재 제약과 확인되지 않은 부분: 코드로 보장되는 것과 의도·가정·미검증 사항을 분리하고 관련 문서로 연결한다.

## 그림과 표현

- 전체 구성 그림 하나와 주요 흐름 그림을 프로젝트 복잡도에 맞게 작성한다. 단일 함수 수준의 작은 도구라면 과도한 서비스 그림 대신 간단한 호출 흐름으로 충분하다.
- 그림의 화살표에는 요청, 데이터, 이벤트, 응답 등 이동하는 것을 적는다. 외부 시스템·저장소·사람의 경계를 구분한다.
- Mermaid, SVG, 텍스트 그림 중 저장소의 미리보기 환경에서 읽히는 형식을 사용한다. 렌더러 의존 형식이라면 그림 밖에도 같은 핵심 흐름을 문장으로 적는다.
- 예시 값과 실제 설정을 구분한다. 키·개인정보·실제 운영 데이터는 문서에 복사하지 않는다.

## 저장 전 확인

- 문서에 적은 경로, 명령, 환경변수, API·이벤트 이름이 저장소에 존재하거나 출처가 분명한가.
- 화살표 방향과 순서가 실제 호출 관계와 일치하는가. 오류·재시도 시 외부 호출 여부를 정확히 적었는가.
- 형식 검증만 하는 코드에 의미적 정확성 보장을 부여하지 않았는가.
- 현재 코드와 다른 계획을 현재 아키텍처처럼 쓰지 않았는가. HANDOFF의 구조 요약 및 README의 실행 방법과 모순되지 않는가.
