# 버그 가능성·취약성 점검 목록

코드를 이 목록에 대어 보고, 걸리는 것만 HANDOFF 4절에 쓴다. 걸리지 않는 항목은 쓰지 않는다.
항목마다 **사용자에게 어떻게 보이는지**까지 적는다. "이벤트 루프를 막음"이 아니라 "여러 명이 동시에 쓰면 뒤 사람이 앞사람 처리 시간만큼 더 기다림".

## 4-1. 동작·성능

| 볼 곳 | 무엇을 찾나 | 예 (여러 도메인) |
|---|---|---|
| 동시 요청 | 비동기 핸들러 안의 동기 호출(외부 API, 파일, DB). 전역 상태 공유 | 비동기 엔드포인트에서 동기 LLM 클라이언트를 부름 → 요청이 하나씩 처리됨. 재현: 느린 가짜 호출 두 개를 동시에 보내 응답 시간을 잰다 |
| 조용히 사라지는 결과 | 검증에 걸린 결과를 버리고 사용자에게 알리지 않음. 다 버려지면 "문제 없음"으로 보이는 **잘못된 통과** | 근거 문장 검사에 걸린 지적을 버림 / 형식이 틀린 재고 행을 건너뛰어 "이상 없음" 표시 / 파싱 실패한 일정을 빼고 요약 |
| LLM 결과 흔들림 | 온도 고정 불가, 경계 입력, 반복 횟수가 적은 테스트 | 경계 입력을 몇 번 돌렸는지 적고, 시연 전 20~30회 권장 |
| 앞단 변환 오류 | 음성 인식·OCR·번역처럼 판정 앞 단계의 오류. 테스트가 그 단계를 건너뛰고 글을 바로 넣는지 | 실제 목소리·잡음·사투리 / 손글씨·기울어진 스캔 / 엑셀 병합 셀 |
| 브라우저·플랫폼 제약 | 마이크·카메라·클립보드(HTTPS 또는 localhost에서만), 브라우저별 녹음 형식 | http + 다른 호스트로 열면 권한 자체가 막힘 |
| 제한 시간 | 외부 SDK 기본 제한 시간·재시도, 화면 쪽 제한 시간 | 응답이 늦으면 화면이 "처리 중"에 오래 머묾 |
| 오류 안내 문구 | 원인과 안내가 맞는지 | 입력이 깨졌는데 "잠시 뒤 다시"라고 안내 |
| 하나만 남기기·정렬 | 여러 결과 중 첫 번째만 쓰는 곳 | 가장 적절한 것이 아닐 수 있음 (설계로 표시) |
| 입력 경계 | 빈 입력, 아주 짧은 입력, 아주 큰 입력, 다른 언어 | 최소 길이 기준을 담당자에게 알렸는지는 3-1에 |

## 4-2. 보안·운영

| 볼 곳 | 무엇을 찾나 |
|---|---|
| 인증·요청 수 제한 | 주소만 알면 누구나 유료 API를 부를 수 있는지. 기본 바인딩 주소(`0.0.0.0`) |
| 요청 크기 | 본문을 전부 읽은 **뒤에** 크기를 검사하는지 |
| 배포 앞단이 제약을 깸 | 프록시의 요청 본문 임시 파일 버퍼링, 접근 로그에 본문·쿼리 문자열 기록 → "저장 금지" 제약 위반 |
| 디버그 로그가 제약을 깸 | SDK·HTTP 디버그 로그가 요청 본문을 남김 |
| 프롬프트 주입 | 사용자 입력을 구분해 넣는지, 결과를 스키마로 받는지, 근거를 검사하는지. 그래도 남는 것 |
| 화면 삽입(XSS) | 결과를 `innerHTML`로 그리는 곳 |
| 의존성 버전 | 고정되지 않은 패키지, 실제 설치 버전, SDK 변경 시 깨질 인자 |
| 키 | 코드·git 기록·로그·오류 메시지에 키가 나오는지 |
| 외부 전송 | 허용된 외부 서비스 외의 주소(CDN, 글꼴, 분석 스크립트) |

## 심각도 기준 (작성자 판단, 문서에 그렇게 밝힌다)
- **높음:** 여러 사람이 쓰면 바로 드러남, 비용·데이터 유출, 합의한 제약 위반
- **중간:** 특정 조건에서 틀린 결과가 맞는 것처럼 보임, 배포 방식에 따라 제약 위반
- **낮음:** 불편하지만 결과는 맞음, 알고 택한 동작
