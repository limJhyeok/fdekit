# Problem Discovery: 문제 정의 노트 + 첫 문의 메시지

과제를 받은 직후 **첫 행동**만 수행한다. 받은 자료만으로 문제를 분해하고, 확인이 필요한 것을 현업이 답할 수 있는 질문으로 바꾼다.

## 범위 (반드시 지킬 것)
- 하지 않는 것: 구현, 기술 스택 선택, 아키텍처 설계, 범위 확정, 메시지 실제 발송.
- 노트와 메시지에 구현 용어(검색, 임베딩, 매칭, DB, API 설계 등)를 넣지 않는다. 구현을 암시하는 해석은 "나중 단계"이므로 적지 않는다.
- 산출물은 두 파일뿐이다. 사용자가 경로를 정하지 않으면 작업 디렉터리에 만든다.
  - `problem-notes.md`
  - `partner-message.md` (현업 대화 채널이 없으면 만들지 않고, 노트의 질문을 '가정 목록'으로 바꾼다)
- 언어는 README의 언어를 따른다.

## 절차

### 1. 받은 자료 확인
작업 디렉터리를 훑어 다음을 확인하고 노트의 '받은 자료'에 적는다.
- 문제 설명(README, task.md 등)
- 데이터 파일: 경로, 형식, 크기
- 시작 코드, 실행 환경, 환경변수, 제출·채점 규칙
- 현업 대화 채널: 담당자 이름과 역할
- **실제 작업 시간:** 사용자가 알려 준 시간이 문제 설명의 시간과 다르면 사용자 쪽을 기준으로 삼고, 노트의 제약에 둘 다 적는다(예: "문제 설명 4시간 / 실제 3시간(사용자 안내)"). 사용자가 말하지 않았으면 문제 설명의 시간을 쓴다.

자료 조합에 따라 3단계의 추가 작업이 정해진다.

### 2. 문제 설명 분해
문제 설명을 처음부터 끝까지 읽고 아래 항목으로 나눈다. **현업 요청 문장은 그대로 인용**한다.

| 항목 | 정리할 내용 |
|---|---|
| 현재 상황 | 지금 무엇이 불편하고, 그 결과 무엇이 일어나는지 |
| 이해관계자 | 요청자 / 현업 파트너 / 실사용자 / 그 밖의 사용자 / 안내를 받는 사람. 현업 파트너의 **기술 배경**(비개발자 / 개발자 / 모름)과 근거를 적는다. 메시지 언어가 여기에 따라 정해진다 |
| 현업 요청 | 원문 인용 + 핵심 표현별 해석 |
| 성공 기준 | 명시 / 추정 / 가설로 나눔 |
| 제약·금지 | 시간(실제 작업 시간 기준), 실행 환경, 허용 기술, 보안, 금지사항. 질문·합의에 쓸 시간 상한(전체의 15~20%)을 분 단위로 계산해 적는다 |
| 과제가 요구하는 활동 | 문서가 직접 요구한 행동. 채점 기준이라고 명시된 것만 그렇게 표시 |
| 핵심 동작 | 결과물이 무엇을 입력받고(음성·이미지·문서·폼 등), 무엇을 판단·분석하고, 결과를 어떻게 보여 주는지. 문제 설명에 정해진 것과 정해지지 않은 것을 나눔 |
| 요청 핵심 표현 | 현업 요청 인용문을 이루는 표현을 뽑은 목록(예: "말해 보고", "고칠 점", "코칭 방식", "부담 없이"). 표현마다 질문 리스트 번호를 하나 이상 연결 |

`references/signal-phrases.md`에 자주 나오는 표현과 그 의미를 정리해 두었다.

### 3. 자료 형태별 추가 분석
- **데이터가 있을 때:** 파일마다 구조(컬럼·섹션), 건수, 분류별 개수, 빈 값, 중복, 형식 이상을 기록한다. 파일이 둘 이상이면 서로 대조한다. 대조 항목은 `references/cross-check.md`에 있다.
- **시작 코드가 있을 때:** 한 번 실행해 보고 구조를 파악한다. 고쳐도 되는 부분과 고정된 부분을 나눠 적는다.
- **문제 설명만 있을 때:** 필요할 데이터·입력이 무엇일지 적되 전부 [가설]로 표시하고 질문 리스트로 넘긴다.

**숫자는 반드시 도구로 센다.** 건수, 조항 수, 분류별 개수, 파일 크기는 `wc`, csv 파싱, `grep -c` 등으로 확인한 값만 적는다. 눈으로 세거나 "약 N개"로 어림하지 않는다.

### 4. 근거 수준 표시
노트의 모든 문장 앞에 근거 수준을 붙이고, 어투를 그에 맞춘다.

| 태그 | 의미 | 어투 | 붙일 것 |
|---|---|---|---|
| **[사실]** | 문서·데이터에 그대로 있음 | "~임" | 출처(파일명, 조항·행 번호) |
| **[추정]** | 근거는 있으나 해석이 들어감 | "~로 보임" | 근거 |
| **[가설]** | 근거 없음 | "~인지 확인 필요" | 질문 리스트 번호 |

### 5. 질문 리스트
노트의 [가설]과 [추정] 중 결과에 영향이 큰 것을 질문으로 바꾼다.
- 종류: 이해관계자 / 우선순위 / 업무 기준 / 모호성 / 사용 맥락 / **제약** / 운영
  - **제약**(데이터 저장·보관, 개인정보, 금지사항, 보안, 외부 공유)은 현업이 먼저 꺼내지 않는 주제다. 문제 설명에 언급이 없어도 **반드시 1개 이상** 넣는다.
- 아래 질문은 **반드시** 넣는다.
  - **입력 방식에서 생기는 질문:** 입력이 음성·이미지·문서처럼 특정 형태라면, 그 형태라서 생기는 판단 기준을 묻는다. 예: 음성이면 말의 내용 말고 말투·속도·머뭇거림·침묵도 보는지, 이미지면 화질·각도를 따지는지.
  - **상호작용 형태 질문:** "~처럼 해 보고", "~하듯이" 같은 표현이 있으면 한 번 하고 끝나는지, 여러 번 주고받는지 묻는다. 예: 응답 한 번인지, 상대와 대화를 이어 가는지.
  - **요청 핵심 표현 질문:** 2단계에서 뽑은 표현마다 질문이 하나 이상 있어야 한다. 특히 "부담 없이", "쉽게", "바로"처럼 기준이 사람마다 다른 표현.
  - **일반화 질문:** 업무 기준을 사례로 묻는 질문에는 "평소 다른 경우에도"를 묻는 후속 질문을 짝으로 둔다. 사례 질문의 답은 그 사례에 묶이기 쉽다.
- 질문마다 **질문 방식**을 정한다. 방식에 따라 문장이 달라진다.

| 방식 | 언제 | 문장 형태 |
|---|---|---|
| 열린 질문 | 자료에 단서가 없는 것(사용 맥락, 업무 흐름) | "주로 누가, 언제 쓰게 될까요?" |
| 해석 확인 | 자료에 있지만 해석이 갈리는 것 | "<파일·항목> '<인용>'을 <내 해석>으로 이해했는데 맞을까요?" |
| 값 인용 | 자료의 값이 최신인지, 공식인지 확인 | "<파일·항목>에는 <값>으로 되어 있는데 지금도 그대로인가요?" |
| 사례 | 업무 기준·예외처럼 말로 정리되지 않은 것 | "최근에 <상황>이 있었을 때 어떻게 처리하셨어요?" |

- 질문마다 **답이 없을 때 쓸 기본 가정**과 **가정의 근거**를 적는다. 근거가 없으면 기본 가정을 비우고 "없음 → 반드시 질문"으로 표시한다.
- 기본 가정이 데이터와 모순되지 않는지 확인한다.

### 6. 자기 검토 (노트 저장 전 필수)
`references/self-review.md`의 체크리스트로 노트 전체를 한 번 훑는다. 걸리는 문장은 태그를 낮추거나, 질문으로 옮기거나, 지운다.

### 7. 노트 저장
`references/notes-template.md` 형식으로 `problem-notes.md`를 쓴다.

### 8. 문의 메시지 작성
`references/message-template.md`의 규칙과 형식으로 `partner-message.md`를 쓴다. 현업 대화 채널이 없으면 이 단계는 건너뛴다.
- 질문을 한 통에 몰아넣지 않는다. **첫 메시지(인사 + 가장 중요한 질문 1~3개)** 와 **이후 차수별 질문 계획**으로 나눈다.

### 9. 사용자에게 보고
짧게 정리해서 알린다.
- 만든 파일 경로
- 문제 한 줄 요약
- 가장 큰 불확실성 3가지
- 메시지는 초안이며 발송하지 않았다는 점
- 답변을 받으면 `requirements-alignment` 스킬로 이어 간다는 점

## 완료 기준
- 문제를 한 줄로 요약할 수 있다.
- 노트의 모든 문장에 근거 수준이 붙어 있고, 숫자는 도구로 확인한 값이다.
- 데이터가 둘 이상이면 대조 결과가 있다. 모순이 없으면 "모순 없음"이라고 적혀 있다.
- 질문마다 질문 방식, 기본 가정과 근거(또는 "반드시 질문")가 있다.
- 제약(저장·개인정보·금지·보안) 질문이 1개 이상 있다.
- 요청 핵심 표현마다 연결된 질문이 있고, 입력 방식·상호작용 형태 질문이 있다.
- 실제 작업 시간 기준의 질문·합의 시간 상한이 분 단위로 적혀 있다.
- 첫 메시지의 질문 1~3개만 답을 받아도 다음 단계를 시작할 수 있다.
