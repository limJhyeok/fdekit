# Quiz: 내가 만든 것을 내 말로 설명할 수 있게

AI와 함께 만든 결과물을 **코드를 보지 않고 5분 안에** 설명하는 연습이다.
원칙은 하나다. **모범 답안은 사용자가 답하기 전에 절대 보이지 않고, 해설은 틀린 칸에만 붙인다.**

- 답안 틀과 유형별 채우는 법은 `references/answer-frame.md`. 채점과 해설은 이 틀을 기준으로 한다.
- 채점은 두 번 한다. 4칸 틀과 모범 답안을 아는 **칸별 채점**(내용)과, 질문·답만 보는 **범용 채점**(실전 채점자가 어떻게 읽는지). 둘의 차이가 형식 때문에 생긴 손해다.

## 시작 전
- 대상 저장소 경로를 정한다(기본: 현재 작업 디렉터리). `git status`로 커밋되지 않은 변경이 있으면 알린다. 문제는 작업 트리 기준으로 낸다.
- 기록 위치: `~/study/<저장소 폴더 이름>/`. **대상 저장소 안에 만들지 않는다.** 제출 스냅샷에 섞이고, 작업 중인 에이전트가 정답 파일을 읽을 수 있다.
- 사용자에게 한 번에 묻는다(AskUserQuestion 가능).
  - 범위: 전체 / 특정 요구사항 ID(R3 등) / 최근 커밋 범위(`<커밋>..HEAD`)
  - 문항 수: 기본 6 (실전 6문항 × 5분)
  - 방식: Closed book(파일을 열지 않고 답함, 기본)
- `STUDY.md`가 이미 있으면 '약한 유형'과 '잘못 이해했던 것'을 읽어 출제 지시에 넘긴다.

## 1. 출제 (새 컨텍스트)
문제를 낸 맥락이 채점까지 하면 모범 답안이 질문에 새거나, 구현한 에이전트가 자기가 잘 아는 곳만 묻는다.
- Agent 도구로 서브에이전트를 띄우고 `references/quiz-prompt.md`를 그대로 보낸다. `<...>`만 채운다. **내가 생각하는 약점이나 결론은 덧붙이지 않는다.**
- 서브에이전트는 두 파일을 쓴다.
  - `~/study/<이름>/quiz-<NN>/questions.md`: 질문만
  - `~/study/<이름>/quiz-<NN>/answer-key.json`: 모범 답안·근거 좌표
- 메인 에이전트는 이 단계에서 `answer-key.json`을 읽지 않는다. 서브에이전트가 돌려준 요약에도 답안이 있으면 사용자에게 옮기지 않는다.

## 2. 질문 품질 점검
`questions.md`와 `answer-key.json`을 `references/question-review.md`로 점검한다. 사용자에게 보이기 전에 한다. (정답 파일을 읽게 되지만 사용자에게는 보이지 않는다. 점검 결과에도 답 내용은 쓰지 않는다.)
- 근거 좌표(`파일:줄`)가 실제로 있고 그 내용을 말하는지 `sed -n`으로 확인
- 일반 지식만으로 답할 수 있는 질문, 5분에 사람이 작성 하기 어려운 질문은 고치거나 뺀다
- 고친 문항 수만 사용자에게 알린다

## 3. 한 문항씩 묻기
- 시작할 때 사용자에게 답안 틀을 한 번 보여 준다(`references/answer-frame.md`):
  - `사실:` → `이유:` → `한계·영향:` → `대응:` 순서로 라벨을 단 짧은 구절. 라벨은 질문에 나온 단어로 바꿔 쓸 수 있고, 순서는 바꾸지 않는다
  - 판단형 질문("충분한가?")만 맨 앞에 질문 말을 받은 판단 한 줄(`충분한가: 아니오 — …`). 설명형 질문에는 쓰지 않는다
  - 인과는 `→`가 아니라 `~므로`로 쓴다. 끝의 `요약:` 한 줄은 시간이 남을 때만
- 문항마다:
  1. `date +%s`로 시작 시각을 기록하고 질문 **하나만** 보여 준다. 유형 이름과 근거 파일은 보여 주지 않는다(힌트가 된다).
  2. 사용자가 답하면 다시 `date +%s`로 걸린 시간을 잰다. 4분 40초를 넘으면 기록에 표시한다(응답 지연이 몇 초 섞인다).
  3. 바로 채점·해설하지 않고 다음 문항으로 간다. 모든 문항을 답한 뒤 4단계로 간다.
- "모르겠다", "패스"도 답으로 받는다. 대신 다그치거나 힌트를 주지 않는다.

## 4. 채점
### 4-1. 범용 채점 (새 컨텍스트)
칸별 채점보다 먼저 한다. `references/generic-grade-prompt.md`를 서브에이전트에 보낸다.
- 넘기는 것은 **질문 원문과 사용자 답 원문뿐**이다. 모범 답안, 하위 질문 목록, 코드, 답안 틀, 내 판정은 넘기지 않는다.
- 결과는 `~/study/<이름>/quiz-<NN>/generic-grade.json`.

### 4-2. 칸별 채점
`references/grading-rubric.md`를 따른다. 문항마다 이때 처음으로 그 문항의 답안 키를 `jq '.questions[] | select(.id=="Q3")'`처럼 꺼내 읽는다.
- 4칸 각각 met / partial / missed / 해당 없음(유형상 생략 가능한 칸)
- 형식 점검: 판단 줄(판단형만), 하위 질문 모두 답함, 라벨·순서, 숫자·함수명·화면 문구 포함, 시간
- 칸 판정은 라벨이 아니라 내용으로 한다. 라벨 문제는 형식 점검에만 남긴다
- 마지막에 `generic-grade-prompt.md`의 비교표로 범용 채점과 맞춰 본다. 내용은 있는데(met·partial) 범용 채점이 unclear·not_answered로 본 하위 질문이 **형식 손해**다
- 잘못 이해한 부분(misconception)은 코드 줄과 나란히 놓고 확인한 것만 쓴다
- 모범 답안과 다른 약점을 짚었어도 실제 코드에 있고 타당하면 met

## 5. 틀린 곳만 해설
partial·missed 칸, misconception, 형식 손해에만 해설을 붙인다. met 칸은 한 줄로 넘어간다.
- 해설은 **코드를 따라가며**: 근거 좌표의 실제 코드를 5~15줄 보여 주고, 그 줄이 왜 그 칸의 답이 되는지 설명한다
- 형식 손해는 범용 채점자가 어디서 막혔는지(인용)와 원인(라벨 없음, 판단형인데 판단 줄 없음, `→` 뜻이 모호함 등), 고친 줄을 보여 준다
- 마지막에 **고쳐 쓴 4칸 답안**(사용자 답을 살려 빠진 칸만 채우고, 라벨을 질문 단어로, 순서를 사실 → 이유 → 한계·영향 → 대응으로 맞춘 것)을 보여 준다. 모범 답안을 통째로 붙이지 않는다
- 이유 칸이 틀렸으면 근거 출처를 구분해 준다: 담당자 합의 / 요구사항 / 내 판단 / 기술 제약 (DECISIONS·conversation-log의 번호로)

## 6. 다시 묻기와 기록
- missed가 있는 칸이 2문항 이상이면, 가장 약한 칸을 다른 각도로 묻는 문항을 1~2개 바로 낸다(같은 코드, 다른 질문). 출제는 1단계와 같은 방식으로 하되 `quiz-<NN>-retry/`에 쓴다.
- `~/study/<이름>/STUDY.md`에 누적한다(형식은 `references/grading-rubric.md` 끝).
  - 회차 표: 날짜, 범위, 문항별 유형·칸 판정·라벨·범용 점수·형식 손해·시간
  - 약한 유형·약한 칸: 최근 3회에서 partial 이하가 반복된 것
  - 형식 습관: 최근 3회에서 형식 손해를 낸 원인
  - 잘못 이해했던 것과 다시 볼 좌표 (다음 회차에서 확인되면 지운다)

## 사용자에게 보고
- 문항별 한 줄: 유형 / 사실·이유·한계·영향·대응 판정 / 범용 점수·형식 손해 수 / 시간
- 형식 손해가 있었으면 다음 회차에 고칠 습관 한 가지
- 가장 먼저 다시 볼 코드 위치 3개 이하
- 다음 회차에 먼저 낼 유형
- 대상 저장소의 파일은 바꾸지 않는다. 해설 중 실제 버그를 찾으면 알리기만 하고, 고칠지는 사용자에게 묻는다
