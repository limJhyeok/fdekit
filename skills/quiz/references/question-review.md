# 질문 품질 점검

사용자에게 질문을 보이기 전에 문항마다 아래를 본다. 걸리면 고치고, 고칠 수 없으면 뺀다(문항 수가 줄면 그대로 진행하고 알린다).
점검 결과를 사용자에게 알릴 때 답 내용은 쓰지 않는다. "Q2 질문 범위를 좁힘", "Q5 근거 좌표 수정"처럼만 쓴다.

## 1. 근거 좌표가 틀림
- `sed -n '<시작>,<끝>p' <파일>`로 읽어 그 칸의 답을 실제로 말하는지 본다. 줄이 밀린 경우가 많다.
- 대화·결정 번호(`#4-2`, `#D3`)는 그 문서에서 `grep`으로 찾는다.
- 이유 칸의 근거 출처 표시(담당자 합의 / 요구사항 / 내 판단 / 기술 제약)가 기록과 맞는지 본다. 응시자가 제안하고 담당자가 동의한 것은 "담당자 합의", 담당자 반대가 없었을 뿐이면 "내 판단"이다.

## 2. 일반 지식으로 답할 수 있음
- **잘못된 질문:** "LLM 호출이 실패하면 어떻게 대응해야 하나?"
- **왜 문제인가:** 코드를 몰라도 "재시도, 사용자 안내, 로그"로 그럴듯하게 답한다.
- **고친 질문:** "`summarize()`에서 OpenAI 호출이 타임아웃되면 사용자는 화면에서 무엇을 보나? 그 상태로 충분한가?"

## 3. 질문이 답을 알려 줌
- **잘못된 질문:** "업로드 파일을 임시 디렉터리에 저장해서 생기는 개인정보 위험은?"
- **고친 질문:** "업로드한 녹음 파일은 처리 후 어디에 남는가? 제약 C2를 지키고 있는가?"

## 4. 5분에 못 씀
- 하위 질문이 4개 이상이거나, 파일 여러 개의 흐름을 모두 따라가야 하는 질문은 하나의 지점으로 좁힌다.
- 모범 답안의 4칸 중 한 칸이 4줄을 넘으면 범위가 넓은 것이다.

## 5. 범위 밖
- 출제 범위(요구사항 ID, 커밋 범위)를 벗어난 코드를 묻는 문항은 뺀다.
- 사용자가 만들지 않은 시작 코드·라이브러리 내부를 묻는 문항은 뺀다.

## 6. must_mention이 채점에 쓸 수 없음
- 코드에 없는 숫자·이름이면 고친다. 너무 흔한 단어("서버", "에러")면 바꾼다.

## 7. 유형 분포
- design_reason, failure_response가 각각 1문항 이상인가
- 같은 유형이 3문항 이상이거나 같은 파일만 묻는 문항이 절반을 넘지 않는가
